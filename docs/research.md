# One shared toolbox ends agents' reinstall loops

Your pain is a real, documented problem across the whole category. AI coding agents and assistants keep losing their environment for three reasons, and every major tool is affected. First, each command runs in a fresh non-interactive shell, or the app is launched from the GUI with launchd's minimal PATH, so venvs, conda, nvm, pyenv and even Homebrew go missing. Second, models are tuned against cloud sandboxes that come preloaded with LibreOffice, pandoc, Poppler and 300+ Python libraries, and a typical laptop has almost none of that. Third, the agents' own OS sandboxes block the package caches, the network and Chromium that the fallback installs need. Benchmarks put a price on this. Microsoft's SetupBench finds that even the best model gets only **62.4%** of environment tasks done, uses **1.13M tokens** per task, and takes **68.8% unnecessary steps**. JetBrains reports that just handing agents the right Python interpreter lifts task success from **68% to 98%**. Existing tools each cover one slice. Container workstations (HolyClaude, DevCell, Docker Sandboxes) give up the host machine. OS sandboxes restrict but install nothing. Rules-sync tools (Ruler, rulesync) copy text without checking that the tools it mentions exist. Package managers (uv, mise, pixi) install tools without telling any agent about them. The open space is a **host-native, container-optional toolbox**: one curated, pinned environment in a stable prefix, with PATH wired for non-interactive shells and GUI apps, and with every agent's instructions, skills, MCP config and sandbox profile generated from a single manifest. It adds a `doctor` command and a policy-gated "add missing package" flow, so the environment grows once instead of being rebuilt every session. One limit up front: no host toolbox can reach inside vendor-controlled cloud sandboxes or the Claude Cowork VM. "Solve them all" means every local process, plus desktop apps through MCP. For this user, a working version of the core idea takes about an afternoon on the current Mac. A check run during this session found that a plain `zsh -c` on this machine resolves `python3` to Apple's 3.9.6 and cannot see Homebrew at all. That one finding explains much of the reinstall loop.

## Three root causes produce nearly every reported failure

The problem catalog is large, but it collapses into three mechanisms, plus a few failure classes that spread out from them. The first mechanism is **process-environment mismatch**. Claude Code documents that "the Bash tool runs each command in a separate process... An `export` in one command won't be available in the next," and tells users to activate their virtualenv *before* launching it ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference.md)). GUI apps fare worse. Claude Desktop "does not source shell profile files like .bashrc or .zshrc, so it has a minimal PATH that may not include /opt/homebrew/bin" ([rapidevelopers](https://rapidevelopers.com/mcp-tutorial/how-to-fix-mcp-server-not-found-error)). Ollama's FAQ says the same of its macOS app, which "never sees export lines in .zshrc" ([Ollama FAQ](https://docs.ollama.com/faq)). A commenter on Codex's most-upvoted nvm issue summarised the shell semantics: nvm in `.bashrc`/`.zshrc` never runs, `~/.profile` only covers `bash -lc`, `~/.zshenv` only covers `zsh -c`, and "`sh -c` and spawned processes read no startup file" ([codex #13566](https://github.com/openai/codex/issues/13566)). IDE and desktop hosts then rebuild PATH themselves and get the order wrong. Claude Code's VS Code extension "incorrectly prepends /usr/bin to PATH" in at least four separate reports ([#41081](https://github.com/anthropics/claude-code/issues/41081), [#84622](https://github.com/anthropics/claude-code/issues/84622)). The Desktop PATH builder put mise/asdf/pyenv shims after `/usr/bin`, so projects ran Ruby 2.6 instead of 4.0 ([#87665](https://github.com/anthropics/claude-code/issues/87665)). Daemon sessions start with `PATH=/usr/bin:/bin:/usr/sbin:/sbin` and cannot find `uvx`, nvm, Homebrew or `~/.local/bin` ([#104181](https://github.com/anthropics/claude-code/issues/104181), open as of 22 Oct 2026). Cursor 2.0 broke `python.terminal.activateEnvironment` in its agent terminal ([Cursor forum](https://forum.cursor.com/t/configured-python-environment-not-activated-in-agent-terminal/141736)).

The second mechanism is **a gap in expected system binaries**. Anthropic's own docx/xlsx/pptx/pdf skills assume that LibreOffice (`soffice`), Poppler (`pdftoppm`), pandoc, qpdf, gcc, npm `docx`/`pptxgenjs`/`sharp`/`react`, and pip `openpyxl`/`pandas`/`markitdown`/`lxml` are "preinstalled" ([docx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/docx/SKILL.md), [xlsx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/xlsx/SKILL.md), [pptx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/pptx/SKILL.md)). That is true inside Anthropic's code-execution container, which ships pandas, python-docx, python-pptx, openpyxl, pypdf, pdfplumber, reportlab and the CLIs unzip, 7zip, rg, fd and sqlite ([Claude code execution docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool)). It is false on a typical Mac. The xlsx case shows the gap is not just about convenience: openpyxl "writes formulas as strings with no cached values," so a correct spreadsheet requires a LibreOffice recalculation pass even for "pure Python" work ([xlsx SKILL.md](https://raw.githubusercontent.com/anthropics/skills/main/skills/xlsx/SKILL.md)). Claude Code's own Read tool "hard fails without poppler" when paging PDFs, and that dependency is undocumented ([#84860 mirror](https://claudeissues.com/issue/84860-read-tool-pages-reroutes-pdf-reading-through-pdftoppm-hard-fails-without-poppler), [#23704 mirror](https://claudeissues.com/issue/23704-bug-read-tools-pdf-support-requires-poppler-utils-but-its-undocumented-usually-a)). When the binary is missing, the agent falls back to `pip install` against Homebrew Python. PEP 668 then blocks it ([PyPA spec](https://packaging.python.org/en/latest/specifications/externally-managed-environments/)), and the agent creates a throwaway venv or reaches for `--break-system-packages`. That is exactly the loop the user describes.

The third mechanism is **the agents' own sandboxes fighting the fallback**. Codex's "Python UV fails in Codex" is the largest single thread found, with 61 comments and 55 reactions ([codex #1457](https://github.com/openai/codex/issues/1457)). Claude Code's sandbox denies writes to `~/.cache/uv` ([#10221](https://github.com/anthropics/claude-code/issues/10221)). Codex on macOS silently ignores `network_access = true` ([codex #10390](https://github.com/openai/codex/issues/10390), open since Feb 2026). Seatbelt profiles in both Codex and Claude Code block Chromium's Mach-port registration, so Playwright cannot launch ([codex #10390](https://github.com/openai/codex/issues/10390), [claude-code #82660 mirror](https://claudeissues.com/issue/82660-bug-macos-sandbox-blocks-chromium-playwright-launch-bootstrap-check-in-denied-no)). LibreOffice cannot bootstrap its user profile in a non-root sandbox. Without a throwaway `-env:UserInstallation`, it "aborts with 'User installation could not be completed' and converts nothing" ([soffice.py](https://raw.githubusercontent.com/anthropics/skills/main/skills/docx/scripts/office/soffice.py)). Agents read the resulting EPERM as a missing package and retry the install, which compounds the loop. That last point is an inference from the issue pattern, not a measured rate.

## Benchmarks put the setup tax at up to 69% wasted steps, and local machines are worse

Measured costs exist, but almost all of them come from Linux-container benchmarks, so they understate local friction. **SetupBench** (Microsoft, 93 tasks across 7 ecosystems, OpenHands harness) finds success rising with model strength, while waste rises faster ([arXiv 2507.09063](https://arxiv.org/html/2507.09063v1)):

| Model | Success | Avg tokens/task | Avg steps | Unnecessary steps vs human-optimal |
|---|---|---|---|---|
| GPT-4o | 34.4% | 303K | 23.2 | 39.4% |
| GPT-4.1 | 50.5% | 436K | 29.5 | 47.9% |
| Claude 3.5 | 53.8% | 455K | 21.6 | 38.2% |
| Claude 3.7 | 57.0% | 869K | 35.7 | 62.7% |
| Claude 4 | 62.4% | 1,129K | 47.1 | 68.8% |

The failure taxonomy matches the local catalog closely. Missing dev tooling (`tox: not found`) causes **17–26%** of repo-setup failures. "Non-persistent environment modifications," meaning `--user` installs or PATH edits that vanish in the next shell, are a named top failure mode. The paper also cites EnvBench/Installamatic findings that **45% of runs failed due to unavailable executables** ([SetupBench](https://arxiv.org/html/2507.09063v1)). **EnvBench** reports that the best method set up only **6.69% of 329 Python repos** versus 29.47% of 665 JVM repos ([arXiv 2503.14443](https://arxiv.org/abs/2503.14443)). **ExecutionAgent** averaged **74 minutes** per project to get test suites running ([arXiv 2412.10133](https://arxiv.org/html/2412.10133v2)). The most striking result is **Repo2Run**: it reached **86.0%** on 420 Python repos, 63.9 points above baseline, mainly through a rollback mechanism that prevents environment "pollution" from failed commands ([arXiv 2502.13681](https://arxiv.org/html/2502.13681v3)). That is direct evidence that environment *state management*, not model intelligence, is the lever.

The most relevant local-machine number comes from **JetBrains**. Across 28 everyday Python-environment tasks and 6 models, average success was **68%** when agents had to find the interpreter themselves and **98%** once PyCharm exposed the configured uv/Poetry/venv/conda interpreter through a skill ([JetBrains blog](https://blog.jetbrains.com/pycharm/2026/08/we-stopped-ai-agents-from-installing-into-the-wrong-python-task-success-rates-jumped-to-95/)). *Caveat: the page returned 403. The figures come from search snippets and a mirror ([dotnetramblings](https://www.dotnetramblings.com/post/12_08_2026/12_08_2026_15/)), and the title says "95%+" while the snippet says 98%.* In practice, telling the agent *where the environment is* removes about a third of failures. The proposed toolbox's whole architecture is built on that finding.

Smaller, softer costs add up around these headline numbers. One practitioner estimates about **2,000 tokens** wasted per conda-activation miss reinstalling packages that already exist, and pip at about 15 s versus uv at about 3 s for pandas ([Vibe Eval](https://blog.vibe-eval.com/content/posts/uv-python-environment-management-2026/); *single-author anecdote*). MCP cold starts via `uvx` took **110 s** for a 68-package server versus 7–26 s warm, which blows through Claude Desktop's hard-coded 60 s initialize timeout ([#84136](https://github.com/anthropics/claude-code/issues/84136)). `npx -y` first runs need 15–30 s against a 10 s default timeout ([rapidevelopers](https://rapidevelopers.com/mcp-tutorial/how-to-use-npx-to-run-mcp-servers); *secondary*). LibreOffice CLI conversions cost about **3.3 s per document**, mostly process start-up ([ask.libreoffice.org](https://ask.libreoffice.org/t/headless-libreofficewriter-slow-to-export-docx-to-pdf/51995)). Three MCP servers consumed **143,000 of 200,000 tokens (72%)** before the first prompt ([Unblocked](https://getunblocked.com/blog/mcp-token-budget-autopsy/); *vendor blog, methodology unverified*). Disk is the quiet cost. On the researcher's Mac, agent-adjacent caches totalled about **9 GB**, including two independent Chrome-for-Testing copies: Playwright at 1.1 GB and Puppeteer at 551 MB (*local measurement*). Whisper weights range from 75 MiB to 2.9 GiB per model, per tool cache ([whisper.cpp on HF](https://huggingface.co/ggerganov/whisper.cpp)).

Two interpretive points matter for design. First, stronger models do not shrink the tax. Claude 4 had the highest success rate but also the most waste in SetupBench, so the fix has to come from the environment, not from waiting for better models. Second, the local-only failure classes (GUI PATH, shims, desktop timeouts, sandbox cache denials) are absent from every benchmark above. No one has published the share of real local agent sessions spent on environment setup. A small open benchmark of local-machine environment tasks would be a credibility asset for the project and does not exist yet.

## Twenty-plus projects cover slices; nobody owns the host machine

The existing landscape splits into five families. Each one solves part of the problem and creates a new gap.

**Security sandboxes** restrict what agents can touch but provide no tools. Anthropic's `sandbox-runtime` uses Seatbelt on macOS and bubblewrap plus seccomp on Linux, and needs "no additional packages" on macOS (6.7k stars, Apache-2.0, beta) ([sandbox-runtime](https://github.com/anthropics/sandbox-runtime), [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)). Codex has `read-only`/`workspace-write`/`danger-full-access` modes ([Codex security](https://learn.chatgpt.com/docs/security)). Gemini CLI has six Seatbelt profiles plus Docker/Podman ([Gemini sandbox](https://geminicli.com/docs/cli/sandbox/)). These are mature enough to *pair with* a toolbox, which is the opportunity.

**Preloaded container workstations** prove the demand but give up the host. HolyClaude packages 8 AI CLIs, a headless browser and 50+ tools in Docker Compose, with privileged capabilities for Chromium (2.6k stars) ([HolyClaude](https://github.com/CoderLuii/HolyClaude)). DevCell offers Docker, Tart macOS VM and Windows VM engines, Nix-based tiers and 11 MCP servers, but lists no office tools and takes about 5 minutes for the first build ([DevCell](https://github.com/devcell-sh/devcell)). Docker Sandboxes (GA January 2026) gives each agent a microVM and supports Claude Code, Codex, Copilot, Gemini and Kiro. It is disposable per sandbox and has no document tools ([Docker blog](https://www.docker.com/blog/docker-sandboxes-run-claude-code-and-other-coding-agents/)). Anthropic's own devcontainer is "a working example rather than a maintained base image," and its feature repo has had no push since December 2025 ([devcontainer docs](https://code.claude.com/docs/en/devcontainer), [GitHub](https://github.com/anthropics/devcontainer-features)). Claude Cowork runs its own Apple Virtualization VM with vendor-controlled tools. It is reported to share `~/.claude/skills` with Claude Code (*secondary, unverified*: [substack](https://aifordevelopers.substack.com/p/the-complete-guide-to-claude-cowork)), and it had a sandbox escape in July 2026 ([The Hacker News](https://thehackernews.com/2026/07/claude-cowork-flaw-could-let-ai-agent.html)).

**Package managers** are fast and agent-agnostic: uv (91k stars, Apache-2.0), mise (35k, MIT), pixi (7.9k, BSD-3), devbox (12k), flox and Nix ([uv](https://github.com/astral-sh/uv), [mise](https://github.com/jdx/mise), [pixi](https://github.com/prefix-dev/pixi)). uv's PEP 723 inline-metadata scripts with a `#!/usr/bin/env -S uv run --script` shebang are the closest existing building block for "a self-contained tool an agent can run" ([uv scripts](https://docs.astral.sh/uv/guides/scripts/)). None of them knows which tools agents need, and none writes instructions for agents. The only agent-targeted package set found is `numtide/llm-agents.nix`, which packages the *agents*, not their tools ([GitHub](https://github.com/numtide/llm-agents.nix)). One open uv feature request asks `uv init` to generate AI-assistant config "similar to `bun init`" ([uv #19677](https://github.com/astral-sh/uv/issues/19677)). Upstream is aware of the gap but has not filled it.

**Instruction and skill sync** has converged on formats but not on discovery paths. AGENTS.md is stewarded by the Linux Foundation's Agentic AI Foundation and used by 60k+ projects ([agents.md](https://agents.md/)). SKILL.md is reported to work in 30–40+ tools (*secondary counts*: [noqta](https://noqta.tn/en/news/skill-md-open-standard-30-ai-coding-tools-adoption-2026)). Precedence still differs between tools. By default, Claude Code reads `AGENTS.md` "only when you have no `CLAUDE.md`" ([Claude Code memory docs](https://code.claude.com/docs/en/memory)), and a secondary study found CLAUDE.md next to AGENTS.md in 56.9% of top repos that ship AGENTS.md ([Towards AI](https://pub.towardsai.net/does-claude-code-read-your-agents-md-we-checked-283-repos-in-161-it-still-reads-claude-md-cb6199708fc1)). Ruler (32+ agents) "never writes MCP configuration files outside your project root" ([Ruler](https://github.com/intellectronica/ruler)). rulesync (70+ tools) has a global mode ([rulesync](https://github.com/dyoshikawa/rulesync)). Both manage text and never check that the tools the text mentions exist.

**MCP registries and gateways** are flooded but aimed at SaaS. The official registry is reported at about 39k servers, **62% of them remote HTTP endpoints** (*secondary*: [dev.to](https://dev.to/amareswer/the-mcp-registry-by-the-numbers-38nc)). Docker's MCP Toolkit rewrites client configs with one click but runs every server as a container ([Docker MCP Toolkit](https://docs.docker.com/ai/mcp-catalog-and-toolkit/toolkit/)). mcpm.sh syncs across clients ([mcpm.sh](https://github.com/pathintegral-institute/mcpm.sh)). Anthropic's own guidance tells users to "install any binaries that local stdio servers depend on in your Dockerfile" ([devcontainer docs](https://code.claude.com/docs/en/devcontainer)). Provisioning the dependencies is left to the user.

| Requirement | Sandboxes | Container workstations | Package managers | Rules sync | MCP managers |
|---|---|---|---|---|---|
| Host-native macOS, no container | ✅ | ❌ | ✅ | ✅ | ◐ |
| Curated, tested toolchain | ❌ | ✅ (Linux) | ❌ (you curate) | ❌ | ◐ MCP only |
| Office/document batteries | ❌ | ? (not confirmed) | ❌ | ❌ | ◐ via servers |
| Shared across all agents + desktop apps | ❌ per-vendor | ◐ CLIs only | n/a | ◐ text | ✅ MCP clients |
| Writes instructions/skills reflecting installed tools | ❌ | ◐ | ❌ | ◐ text, unverified | ❌ |
| PATH fixed for GUI and non-interactive shells | ❌ | n/a (inside box) | ❌ | ❌ | ◐ |
| Doctor/verification | ❌ | ❌ | ◐ per tool | ❌ | ❌ |

The empty column is the opportunity: **host-native + curated + document-capable + cross-agent + self-describing + verified**. No surveyed project is positioned this way. *That absence is not proof. GitHub search was rate-limited during the research, and small projects may exist.* The landscape also carries a durability warning. Daytona archived its open-source repo in June 2026, Gitpod Classic was sunset, textcortex's sandbox was archived, and dotagents and vibekit have gone quiet ([Daytona](https://github.com/daytonaio/daytona), [Ona](https://ona.com/stories/gitpod-classic-payg-sunset), [textcortex](https://github.com/textcortex/claude-code-sandbox)). The toolbox should be thin glue over durable upstreams (Homebrew, uv, mise, aqua) so that it survives its own maintainers moving on.

## Architecture: one host-native prefix, one manifest, many adapters

The design principle follows from the evidence. **Don't invent a package manager, don't require a container, and don't trust shell initialization.** Install a curated set of tools once into a stable prefix with absolute paths. Then *project* that one source of truth into every place an agent looks: PATH for every shell mode, instruction files, skill folders, MCP configs and sandbox allowlists. Throughout this section, the working name is `agentkiln` with binary `kiln` (see the naming section).

```
                         recipes (TOML, schema-validated, signed index)
                                          │
                                 kiln.lock  (resolved, pinned, hashes)
                                          │
        ┌──────────────── ~/.agentkiln/ (one shared, persistent env) ────────────────┐
        │ bin/        namespaced shims: kiln-py, kiln-node, soffice-safe, pandoc...   │
        │ py/         uv project (Python 3.12 pinned) + uv.lock  → .venv              │
        │ node/       npm prefix (docx, pptxgenjs, sharp...)                          │
        │ sys/        links to brew/apt/winget/aqua-installed binaries                │
        │ share/      fonts, tesseract langs, PLAYWRIGHT_BROWSERS_PATH, HF_HOME       │
        │ skills/     generated SKILL.md per battery (what's installed + how to call)  │
        │ manifest.json  machine-readable capability list (versions, abs paths)       │
        └────────────────────────────────────────────────────────────────────────────┘
              │ PATH wiring         │ instruction/skill fan-out    │ MCP + sandbox
   ~/.zshenv, BASH_ENV,      ~/.claude/CLAUDE.md (import)    abs-path MCP entries in
   launchd env, Windows      ~/.gemini/GEMINI.md, Codex       Claude Desktop/Cursor/Codex;
   user PATH, SessionStart   AGENTS.md, Cursor rules, skill   srt/Codex/Gemini profiles
   hook → CLAUDE_ENV_FILE    dirs per agent                   allowing prefix + caches
                                          │
                                   kiln doctor [--json] [--fix]
```

### Native-first on every OS, containers as a generated second target

The backends are the platform's best existing installers. On macOS, use Homebrew formulae and casks for system binaries (LibreOffice, pandoc, Poppler, qpdf, tesseract, ffmpeg, duckdb, fonts). On Linux, use apt/dnf where available, falling back to aqua-style vendor tarballs without root. On Windows, use winget/Scoop. Everywhere, use **uv for Python**, an **npm prefix for Node libraries**, and optionally mise/aqua for CLI version pinning and pixi/Nix for users who want stronger reproducibility. mise's move away from asdf plugins toward aqua's declarative metadata with checksum, Cosign, SLSA and GitHub-attestation verification is the right model to copy ([mise registry](https://mise.jdx.dev/registry.html), [aqua backend](https://mise.jdx.dev/dev-tools/backends/aqua.html)). The *same lockfile* also emits a Dockerfile, a Dev Container Feature and a Docker Sandboxes template for users who want isolation. Containers then come out of the toolbox as an output, rather than the toolbox depending on them, which reverses the HolyClaude/DevCell approach. Inside a container or the Cowork VM, the toolbox can only help if the user builds that image from the lockfile. This boundary should be documented explicitly.

### One shared env that does not shadow project environments

The shared environment exists for *ad-hoc work outside a project*, such as "edit this docx" or "summarize this xlsx". It must never compete with a project's own venv. JetBrains' 68%→98% result comes from agents using the project's interpreter, so the toolbox should reinforce that rule, not undermine it. The concrete rule: the toolbox **never puts a bare `python`, `python3` or `node` first on PATH**. It exposes namespaced entry points instead (`kiln-py`, `kiln-node`, `kiln-run script.py`). Generated instructions say: "inside a project with `pyproject.toml`/`.venv`, use `uv run`; for one-off document or data work, use `kiln-py`". The shared Python should be **pinned to 3.12** (or 3.13 once the batteries' wheels are verified), not the newest Homebrew minor version. This avoids the 3.14 wheel gaps ([torch 3.14](https://github.com/rohitg00/ai-engineering-from-scratch/issues/192)) and the silent breakage when `brew upgrade` moves `python3`. Aider did the same thing for the same reason ([Simon Willison](https://simonwillison.net/2025/Mar/6/aider-using-uv-as-an-installer/)), and its uv-isolated installer "dramatically reduced the number of GitHub issues from users with conflicted/broken python environments." Batteries live in uv dependency groups (`office`, `pdf`, `data`, `media`) inside a single `uv.lock`, so they resolve together without conflicts. A battery that cannot co-resolve becomes its own isolated `uv tool` environment with a shim, which is the same isolation Aider uses. For one-off scripts that need exotic packages, PEP 723 scripts run through `kiln-run` share the uv cache instead of building a new venv each time.

### PATH wiring for every launch mode

PATH has to be fixed at every place a process gets its environment, because no single file covers them all. For zsh, write a guarded block into `~/.zshenv`, which zsh reads for *all* shells including `zsh -c`. For bash, write `~/.profile` and set `BASH_ENV` to a small kiln env file. The nvm README itself recommends `BASH_ENV` for non-interactive bash ([nvm README](https://github.com/nvm-sh/nvm/blob/master/README.md)). For Claude Code, install a SessionStart hook that writes to `CLAUDE_ENV_FILE`, the documented way to persist variables across Bash calls ([hooks docs](https://docs.claude.com/en/docs/claude-code/hooks)). This has to cope with the open bugs where `/resume` loses the env and Windows truncates past about 8 KB ([#98933](https://github.com/anthropics/claude-code/issues/98933), [#103861](https://github.com/anthropics/claude-code/issues/103861)), so keep the payload tiny: just the prefix prepend. For Codex, generate `shell_environment_policy` entries (`set`, `include_only`) ([Codex config reference](https://learn.chatgpt.com/docs/config-file/config-reference)). For macOS GUI apps, the robust fix is **absolute paths in every generated config**, because "setting PATH in the env block of the MCP config is not reliable across all hosts" ([rapidevelopers](https://rapidevelopers.com/mcp-tutorial/how-to-fix-mcp-server-not-found-error)). An optional LaunchAgent can set launchd's environment, following the `launchctl setenv` pattern Ollama documents ([Ollama FAQ](https://docs.ollama.com/faq)). *Whether a LaunchAgent-set PATH reliably reaches Electron apps launched from the Dock is unverified and must be tested per app.* On Windows, update the user PATH in the registry and write `cmd /c` wrappers for `.cmd` shims ([mcpcat](https://mcpcat.io/guides/fixing-mcp-error-32000-connection-closed/)). The toolbox should also *detect* the snapshot hazards it cannot fix, such as aliases named `ls`, `grep` or `hash` that Claude Code's snapshot will replay ([#91600](https://github.com/anthropics/claude-code/issues/91600), [#101498](https://github.com/anthropics/claude-code/issues/101498)), and offer to guard them behind an interactive-shell check.

### Instruction and skill generation into each agent's own path

The manifest is turned into text in two forms. The first is a short **machine-level instructions block**: what's installed, the absolute prefix, the "project env first, `kiln-py` otherwise" rule, "never `--break-system-packages`, run `kiln need <pkg>` instead," and the non-interactive flags (see the process subsection). The second is **one SKILL.md per battery** with exact invocations: `soffice-safe --convert-to pdf`, the xlsx recalc step, `pdftotext -layout` before reading big PDFs. Skills load by progressive disclosure, at about 100 tokens of metadata until needed ([Atlan](https://atlan.com/know/ai-agent/ai-agent-skills/what-are-agent-skills/)). That makes them far cheaper on context than MCP tool schemas. The fan-out writes a marked, idempotent block (`<!-- agentkiln:begin -->`…`<!-- agentkiln:end -->`) into each target. Targets are the user-level CLAUDE.md, imported rather than relying on AGENTS.md because of Claude's precedence rule ([memory docs](https://code.claude.com/docs/en/memory)), the user-level GEMINI.md ([Gemini docs](https://geminicli.com/docs/cli/sandbox/)), Codex's home config directory, Cursor and Cline rules, and each agent's skills directory. *The exact global paths for Codex AGENTS.md, Cursor's user rules (`.mdc`) and native SKILL.md discovery in Cursor and the desktop apps are not verified from primary docs. Each adapter needs a verified-path test before release.* rulesync already covers 70+ tool layouts, so the toolbox can call it as a backend for repo-level fan-out rather than duplicate it ([rulesync](https://github.com/dyoshikawa/rulesync)). The key difference from rulesync is that every generated line traces back to a manifest entry that `doctor` has verified.

### MCP wiring that removes the cold-start failure class

Every MCP server the toolbox manages is **pre-installed** (`uv tool install`, npm prefix) and referenced by **absolute path**, never `npx -y`/`uvx` at launch. This turns 15–110 s network-bound cold starts into local exec and removes most ENOENT failures. Generated entries set the per-host timeouts that exist: Codex `startup_timeout_sec`/`tool_timeout_sec` ([Codex config](https://learn.chatgpt.com/docs/config-file/config-reference)) and Claude Code's `MCP_TIMEOUT` (*default unconfirmed*). They also wrap servers in a stderr-only launcher that redirects stray stdout logging, the "single most common bug in custom MCP servers" ([rapidevelopers](https://rapidevelopers.com/mcp-tutorial/how-to-fix-mcp-json-rpc-parse-errors)). For hosts that cannot run shell commands, mainly desktop chat apps, ship **one optional, small `kiln-mcp` server**. It exposes `list_capabilities`, `convert_document` and `run_kiln_script` instead of dozens of tools, which keeps the context bloat documented above in check. Environment variables in MCP configs should hold references to the OS keychain, not literal keys (see secrets).

### Sandbox profile generation instead of sandbox bypass

Agents escalate to `danger-full-access` when sandboxes block caches, network or browsers ([codex #10390](https://github.com/openai/codex/issues/10390)). The toolbox should therefore *generate* least-privilege profiles that make its tools work inside the sandbox. That means `~/.srt-settings.json` entries for sandbox-runtime, Codex `writable_roots` and network settings, and a Gemini Seatbelt profile. Each grants read and execute on the prefix, write on its own caches (`~/.cache/uv`, the npm cache, `PLAYWRIGHT_BROWSERS_PATH`, a per-call LibreOffice profile directory), and network only for named registries during `kiln need`. The `soffice-safe` wrapper always passes a fresh `-env:UserInstallation=file:///tmp/lo_<id>`, which avoids both the profile-bootstrap abort and the single-instance silent no-op ([LO bug 37531](https://www.libreoffice.org/bugzilla/show_bug.cgi?id=37531)). It can optionally keep a resident unoserver for batch speed ([Transloadit](https://transloadit.com/devtips/automate-document-conversion-in-rust-with-unoserver/)). Headless Chromium cannot launch under current Seatbelt profiles without a `mach-register` allowance ([codex #10390](https://github.com/openai/codex/issues/10390)). The honest guidance is to run browser MCP servers outside the agent sandbox through a scoped launcher, pointed at one shared browser install, which also removes the duplicate-Chrome disk cost.

### The doctor command is the product's front door

`kiln doctor` checks four things: every battery's binary runs and reports its expected version; each shell mode (`zsh -c`, `bash -c`, login, launchd, each detected agent) resolves the prefix; each agent's instruction file contains a current kiln block and no conflicting CLAUDE.md/AGENTS.md precedence trap; and each MCP entry uses absolute paths and starts within its timeout. It also flags secrets in plaintext configs, Homebrew Python being the target of agent `pip` calls, duplicate browser caches, and sandbox profiles missing cache paths. It emits ✓/✗/! lines with fix hints, `--json` for agents and CI, and `--fix` for safe repairs. The `--json` mode matters most, because agents can self-diagnose with it ("run `kiln doctor --json` when a tool is missing") instead of guessing and reinstalling. The doctor output also serves as the bug-report template.

### Self-growing "add missing package" flow

This flow ends the reinstall loop. When an agent needs something absent, the instructions tell it to run `kiln need openpyxl`, or `kiln need --bin pandoc`, instead of creating a venv. The command resolves the name against the recipe index. A **curated recipe** installs into the shared env, updates `kiln.lock`, regenerates the manifest and skills, and prints the absolute path to use. An **unknown PyPI or npm name** asks the user, or follows a pre-set policy (`auto`/`ask`/`deny`), checks the name against typosquat lists, and records provenance, because agent-driven installs are a supply-chain vector. Every mutation takes a lockfile snapshot first and rolls back automatically if import or smoke tests fail. This is Repo2Run's rollback idea, which accounted for its 63.9-point lift ([Repo2Run](https://arxiv.org/html/2502.13681v3)). The next session, and every other agent, sees the package already installed and documented. The environment grows monotonically and never gets rebuilt. A weekly `kiln prune` reports batteries that no session has used.

### Secrets hygiene by construction

Agents inherit the full shell environment and can read `.env` files despite deny rules ([The Register](https://www.theregister.com/2026/01/28/claude_code_ai_secrets_files/), [#24846](https://github.com/anthropics/claude-code/issues/24846)). Codex's documentation is ambiguous about whether KEY/SECRET/TOKEN variables pass through by default ([Codex config](https://learn.chatgpt.com/docs/config-file/config-reference); *literal reading suggests they do*). The toolbox should never write secrets into generated files. MCP and CLI credentials go through a `kiln secret` indirection backed by the macOS Keychain, Windows Credential Manager or libsecret, resolved at process launch by the wrapper. `doctor` should flag exported API keys in `.zshrc`, plaintext keys in `claude_desktop_config.json` (which may sync to backups ([checklist](https://pranoti.thesciencetalk.com/ai-guides/mcp-security-checklist-claude-desktop/))), and missing `Read(./.env*)` deny rules ([settings docs](https://code.claude.com/docs/en/settings)). It should note that read-deny rules do not stop `cat .env` unless the OS sandbox also blocks the path. The kiln env file and SessionStart payload must contain only PATH-like variables, never credentials.

### Process and timeout guidance shipped as config, not advice

The generated instructions and env file should set the non-interactive defaults that prevent most hangs. Those are `GIT_PAGER=cat`, `PAGER=cat`, `GIT_EDITOR=true`, `CI=1` where safe, `npm init -y`/`--yes` conventions, and `sudo -n`. They should also say to run dev servers in the background with a log file, never in the foreground. *This list is standard practice and was not found in one primary source.* The guidance should reflect real limits: Claude Code's 2-minute default and 10-minute maximum foreground timeout and 30k-character output cap ([tools reference](https://code.claude.com/docs/en/tools-reference.md)). It should also cover hazards: background respawn storms ([#37490](https://github.com/anthropics/claude-code/issues/37490)), orphaned MCP processes ([#1935](https://github.com/anthropics/claude-code/issues/1935)), and IDE agents losing completion signals under heavy prompts like Powerlevel10k, where a minimal prompt when `TERM_PROGRAM == vscode` is the documented workaround ([Cursor forum](https://forum.cursor.com/t/terminal-commands-get-stuck-hang-when-running-in-cursor-agent-mode/134314), [Cline docs](https://docs.cline.bot/troubleshooting/terminal-integration-guide)). A `kiln reap` command lists and kills orphaned MCP servers and LibreOffice instances. On Windows, the toolbox sets `PYTHONUTF8=1` and `PYTHONIOENCODING=utf-8` for its own processes, given the cp1252 crash cluster ([#7582](https://github.com/anthropics/claude-code/issues/7582), [#60378](https://github.com/anthropics/claude-code/issues/60378)).

## Declarative recipes, two review tiers, and Homebrew-grade provenance

### Recipe schema

Recipes should declare *what* to install, never *how*, and be validated against a published JSON Schema. The precedent is MCP's `server.json` and Dev Containers' `devcontainer-feature.json` ([containers.dev](https://containers.dev/implementors/features-distribution/)). mise stopped accepting asdf/vfox plugins because arbitrary install code "can do a lot of damage" ([mise registry](https://mise.jdx.dev/registry.html)). A recipe ties package backends to the agent-facing layer, which is the part no other ecosystem has:

```toml
schema = "agentkiln/recipe/v0"
id = "office.docx"
summary = "Create, edit, read and render Word documents"
maintainers = ["github:alice", "github:bob"]
license_note = "LibreOffice MPL-2.0; pandoc GPL-2.0+"

[provides]
bins = ["pandoc", "soffice-safe", "pdftoppm"]
python = ["python-docx>=1.1", "markitdown[docx]", "lxml", "defusedxml"]
node = ["docx@^9"]

[install.macos]
brew = ["pandoc", "poppler"]
cask = ["libreoffice"]
[install.debian]
apt = ["pandoc", "libreoffice-writer-nogui", "poppler-utils"]
[install.windows]
winget = ["JohnMacFarlane.Pandoc", "TheDocumentFoundation.LibreOffice"]
scoop = ["poppler"]

[verify]                     # declarative smoke tests run by doctor and CI
commands = ["pandoc --version", "soffice-safe --version"]
python_imports = ["docx", "markitdown"]
fixture = "tests/hello.docx -> pdf"

[agent]
skill = "skills/docx/SKILL.md"           # templated with abs paths at sync time
instructions = "Read with `pandoc -t markdown`; render via `soffice-safe --convert-to pdf`."
sandbox = { write = ["/tmp/lo_*"], exec = ["soffice-safe"] }

[deprecated]                 # optional: date, reason, replacement
```

*The Windows package IDs and the Debian package names above are drafts from the research notes and were not individually verified.*

### Contribution model and supply chain

Copy the structures that scaled. The first is a **curated core index plus permissionless namespaced taps**: Homebrew's core-plus-taps escape valve ([Acceptable Formulae](https://docs.brew.sh/Acceptable-Formulae)), with MCP Registry-style `io.github.<user>/` namespaces that are verified through GitHub OIDC, which blocks impersonation and covers OpenSSF's typosquatting requirement ([modelcontextprotocol.info](https://modelcontextprotocol.info/tools/registry/)). The second is **per-recipe CODEOWNERS** in one monorepo, the conda-forge per-feedstock model in miniature ([conda-forge governance](https://conda-forge.org/community/governance/)). The third is a **bot that opens version-bump PRs**, which is what lets conda-forge's volunteer teams keep up ([conda-forge sub-teams](https://conda-forge.org/community/subteams/)). The fourth is a **CI matrix** that runs every recipe's `[verify]` block on macOS arm64, Linux x86_64/arm64 and Windows, following the Dev Container Features `test/` convention. For provenance, verify upstream checksums and attestations at install time, aqua-style ([aqua backend](https://mise.jdx.dev/dev-tools/backends/aqua.html)). Sign your own releases and the recipe index with Sigstore and GitHub attestations, as Homebrew does for every bottle ([Sigstore blog](https://blog.sigstore.dev/homebrew-build-provenance/)), and publish through OIDC trusted publishing. Target OpenSSF Level 1 at launch: MFA, a 90-day disclosure policy, name-similarity checks and lockfile pinning. Reach Level 2–3 by v1.0: malware scanning, install-time vulnerability warnings, provenance and SBOMs ([OpenSSF principles](https://repos.openssf.org/principles-for-package-repository-security)). Homebrew's hardening was paid for by an OpenSSF Alpha-Omega grant, which is a realistic funding path for this work too ([Alpha-Omega](https://alpha-omega.dev/blog/alpha-omega-grant-to-help-homebrew-reach-slsa-build-level-2/)). Arbitrary-code hooks, such as post-install scripts, should go in a separate, higher-scrutiny tier that is off by default.

### Governance, licensing and neutrality

Neutrality is a feature here. The underlying standards (MCP, AGENTS.md, goose) moved to the Linux Foundation's Agentic AI Foundation in December 2025, with Anthropic, OpenAI, Google and Microsoft as members ([LF press release](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). The uv community debated its independence after OpenAI acquired Astral in March 2026 ([Simon Willison](https://simonwillison.net/2026/Mar/19/openai-acquiring-astral)). That is a reason to keep uv as one swappable backend rather than the only one, and to keep the toolbox vendor-neutral so every agent vendor can safely reference it. Start with a small maintainer team, a GOVERNANCE.md, an RFC folder for schema changes only, and the Contributor Covenant. Keep the path to AAIF or a fiscal host open. On licensing, *background norms not verified this session*: dual **MIT OR Apache-2.0** for code maximizes compatibility and adds Apache's patent grant, and recipes and skills can go under CC0 or MIT. The toolbox must surface upstream licenses such as LibreOffice MPL and PyMuPDF/Ghostscript AGPL in recipe metadata, because users will redistribute container exports.

### Telemetry and distribution

Copy Homebrew's analytics norms: no user identifier or IP field, a notice before any event is sent, one-command and env-var opt-out, 365-day retention, and public aggregates ([Homebrew Analytics](https://docs.brew.sh/Analytics)). For this audience, go further. Make telemetry **opt-in**, respect `DO_NOT_TRACK` (*adoption unverified*), disable it in CI, and never send prompts, paths, package names outside the curated index, MCP URLs or anything from config files. Distribute a static Rust or Go binary, which avoids the bootstrap problem of a Python tool needing Python. Channels: a short, version-pinnable `install.sh`/`install.ps1` with SHA256 verification and `--dry-run`, a Homebrew tap (moving to homebrew/core once it meets the stable-tag criteria ([Acceptable Formulae](https://docs.brew.sh/Acceptable-Formulae))), thin `npx`/`uvx` wrappers that download the platform binary (the most natural first touch for agent users who already have Node), and winget/Scoop manifests. On Windows, generate config files rather than symlinks, because symlinks need developer mode. For growth, uv's path (benchmarks in the README, one-line install, 126M+ monthly downloads per *secondary* reports ([noqta](https://noqta.tn/en/news/openai-acquires-astral-python-tooling-uv-ruff-codex-2026))) suggests leading with a measurable claim. An example: "a docx→pdf task in Claude Code: N reinstalls before vs zero after, X tokens saved", shown as a 15-second demo of `kiln init` configuring five agents at once.

## Your Mac today: three Pythons and a PATH that hides Homebrew

A read-only check run during this session explains the user's loop concretely (*local measurement, 27 Oct 2026*). The machine has **Homebrew Python 3.14.6** (`/opt/homebrew/bin/python3`), a **python.org framework 3.14.5** (`/usr/local/bin/python3`), **Apple's 3.9.6** (`/usr/bin/python3`), and a **uv-managed CPython 3.12.13** that is already downloaded. Homebrew's PATH setup lives only in `~/.zprofile`, which login shells read. `~/.zshenv` sources only `~/.cargo/env`. As a result, a clean `zsh -c`, the shell mode many agents and GUI-spawned tools use, gets `PATH=~/.cargo/bin:/bin:/usr/bin:/usr/ucb:/usr/local/bin`. That PATH resolves `python3` to **Apple's 3.9.6** and finds **no `brew`, `uv` or `node`**. The launchd user PATH is unset, so Dock-launched apps get the system default. `soffice`, `pandoc`, `qpdf`, `gs`, `tesseract`, `magick` and `duckdb` are missing. `pdftoppm`, `ffmpeg`, `fd`, `node`, `uv`, `jq`, `sqlite3` and Docker are present. Claude Code's shell snapshot is visible in action: `rg` resolves to a function defined in `~/.claude/shell-snapshots/`. There is no `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md` or `~/.gemini/GEMINI.md`, and Claude Desktop's config has no MCP servers. So an agent asked to edit a docx finds no pandoc or LibreOffice. It may land on a Python where `pip` is PEP 668-blocked, or on Apple's 3.9. It builds a temp venv, and nothing tells the next session that any of this happened.

The steps below build a manual version of the toolbox's MVP in about an afternoon. They double as the prototype that validates the design before any code is written.

| Step | Action | Why |
|---|---|---|
| 1 | `brew install pandoc qpdf tesseract tesseract-lang ghostscript duckdb` and `brew install --cask libreoffice` | Closes the office/PDF/OCR binary gap the skills assume |
| 2 | Install metric-compatible fonts (Carlito, Caladea, Liberation, Noto Sans CJK) via Homebrew casks (*cask names unverified; check `brew search font-carlito`*) | LibreOffice render fidelity |
| 3 | Create the shared env on the already-installed 3.12: see the code block below | One pinned env, not Homebrew 3.14, not throwaway venvs |
| 4 | `npm install --prefix ~/.agentkiln/node docx pptxgenjs sharp react react-dom react-icons` | Node libs the docx/pptx skills expect |
| 5 | Create `~/.agentkiln/bin/` with namespaced shims (`kiln-py`, `kiln-node` setting `NODE_PATH`, `soffice-safe` adding `-env:UserInstallation=file:///tmp/lo_$$`) | Avoid shadowing project interpreters; fix the LibreOffice lock and profile issue |
| 6 | Add to the top of `~/.zshenv`: `export PATH="$HOME/.agentkiln/bin:/opt/homebrew/bin:/opt/homebrew/sbin:$PATH"` | Makes Homebrew and the toolbox visible to `zsh -c`; verify with `env -i HOME=$HOME zsh -c 'command -v pandoc kiln-py uv'` |
| 7 | Write a short marked block into a new `~/.claude/CLAUDE.md`, and the same text into `~/.gemini/GEMINI.md` and Codex's global AGENTS.md (*verify Codex's path in its docs*): installed tools, absolute paths, "project env first via `uv run`; otherwise `kiln-py`; never `--break-system-packages`; to add a package run `uv add --project ~/.agentkiln/py <pkg>`" | The JetBrains effect, and the start of the "grow once" flow |
| 8 | Copy Anthropic's docx/xlsx/pptx/pdf skills into `~/.claude/skills/` (and other agents' skill dirs), editing "preinstalled" lines to point at the shims | Skills now match reality |
| 9 | For any MCP server in Claude Desktop/Cursor, use absolute paths to pre-installed binaries (`uv tool install …`), never bare `npx -y`/`uvx` | Removes ENOENT and cold-start timeouts |
| 10 | If you use Claude Code's `/sandbox` or Codex `workspace-write`, allow read/exec on `~/.agentkiln`, write on `~/.cache/uv` and `/tmp/lo_*` | Prevents EPERM-driven reinstall loops |
| 11 | Keep Docker for optional `sbx` autonomy runs; don't build the MVP on it | Native-first; containers later from the lockfile |
| 12 | Write a 10-line smoke script (docx→md, docx→pdf, xlsx recalc, pdf→text, OCR one page) and run it from `zsh -c`, Claude Code, Codex and Claude Desktop. That script is `kiln doctor` v0 | Proves the design; becomes the first CI test |

```bash
mkdir -p ~/.agentkiln/bin && cd ~/.agentkiln
uv init --bare --python 3.12 py && cd py
uv python pin 3.12   # writes .python-version so uv never picks Homebrew 3.14
uv add python-docx openpyxl xlsxwriter python-pptx pandas "markitdown[all]" \
       pypdf pdfplumber pypdfium2 reportlab pytesseract pdf2image Pillow lxml defusedxml \
       duckdb pyarrow
uv sync            # creates ~/.agentkiln/py/.venv with a committed uv.lock
ln -sf ~/.agentkiln/py/.venv/bin/python ~/.agentkiln/bin/kiln-py
```

For the open-source project itself, the immediate moves are four. First, check the `agentkiln` GitHub org, domain and trademark, plus the `kiln` binary name, before anything public. Second, put this manual setup in a repo as a Brewfile, `uv.lock`, the shim scripts, generated instruction blocks, and the smoke test, under MIT OR Apache-2.0, as a "0.0" that others can try. Third, draft recipe schema v0 from the four batteries above. Fourth, write the native binary only after the manual prototype has run for two weeks across Claude Code, Codex, Gemini CLI and Claude Desktop, logging every remaining environment failure. That log becomes the first set of `doctor` checks and the launch post's evidence.

## Conclusion

The research changes the framing from "agents are bad at environments" to "agents are blind to environments." Two of the best results in the data come from making existing state visible, not from smarter models: JetBrains' lift from exposing the interpreter, and Repo2Run's lift from protecting environment state. Meanwhile, stronger models in SetupBench spent *more* steps on setup. That makes the toolbox's real product the **manifest that `doctor` has verified and that every agent reads**, more than any installed package. It also means the project should measure itself on "installs per session trending to zero," not on how many tools it ships. Doing this well also creates a data asset no vendor has: an open benchmark of local-machine environment failures.

The hard limits are just as clear. A host toolbox cannot reach into vendor cloud sandboxes or the Cowork VM. It can only reach desktop chat apps through MCP. Its PATH fixes depend on vendors' shifting snapshot and env-file implementations, which are themselves open bug clusters. The winning position is therefore *thin, neutral glue*. It sits over Homebrew, uv, aqua and the OS sandboxes, speaks AAIF formats, and upstreams adapters into the agents. A defensible open-source project is one that agent vendors can point to in their own setup docs, because it belongs to none of them.
